# Local LLM Optimizer: 이론부터 구현까지

## 1. 이 프로젝트가 해결하는 문제

같은 모델이라도 PC와 실행 설정에 따라 속도·메모리 사용량이 달라집니다. 문맥을 크게 잡아 VRAM을 넘기면 일부 계산이 CPU로 이동하면서 느려질 수 있고, 너무 작게 잡으면 필요한 문서가 들어가지 않습니다.

따라서 목표를 다음처럼 정의합니다.

> 특정 모델에서, 필요한 문맥 길이와 시스템 메모리 한도를 만족하는 설정 중 생성 속도가 높은 설정을 찾는다.

답변 품질은 별도로 확인해야 합니다. 모델 크기가 다른 후보의 정답률까지 평가하지 않고 전체 1위를 뽑으면 작은 모델에 유리한 잘못된 결론이 나올 수 있습니다.

## 2. VRAM을 차지하는 세 부분

```text
대략적인 VRAM = GPU에 올라간 모델 가중치 + GPU의 KV 캐시 + 연산용 버퍼/런타임
```

### 모델 가중치

모델이 학습한 수치입니다. 단순 근사로 `매개변수 수 × 비트 수 ÷ 8` 바이트입니다.

4B 모델을 전부 4비트로 저장하면 순수 수치만 약 2GB(십진)입니다. 실제 양자화 파일에는 부가 정보와 다른 정밀도의 텐서가 있으므로 이보다 커질 수 있습니다. 파일 크기와 실제 VRAM 사용량도 같지 않습니다.

기존 Q4 모델을 다시 Q4로 선택한다고 메모리가 추가로 절반이 되지는 않습니다. 먼저 `ollama show qwen3:4b`에서 현재 양자화를 확인해야 합니다.

### KV 캐시

이전 토큰의 attention 계산에 필요한 Key와 Value를 저장합니다. 일반적인 dense attention 모델의 근사는 다음과 같습니다.

```text
KV bytes ≈ 토큰 수 × 레이어 수 × KV head 수 × head 차원 × 2(K와 V) × 값당 바이트
```

GQA처럼 KV head 수를 줄이는 구조는 캐시도 작아집니다. sliding window, 하이브리드 구조 등에서는 식이 달라질 수 있습니다. 실행 엔진이 설정된 문맥을 미리 할당하는지도 영향을 줍니다.

KV 캐시만 f16에서 q8로 바꾸면 캐시 공간은 대략 절반, q4로 바꾸면 대략 1/4이 됩니다. 전체 VRAM이 같은 비율로 줄어들지는 않습니다. 양자화 부가 정보와 품질 영향도 있습니다. [Ollama FAQ](https://docs.ollama.com/faq)

### 연산용 공간

입력을 처리할 때의 임시 텐서, 계산 그래프, GPU 런타임 등이 사용합니다. 배치 크기와 backend, Flash Attention 지원 여부에 따라 달라집니다.

## 3. 조절하는 값의 의미

| 설정 | 바꾸는 것 | 일반적인 절충 |
|---|---|---|
| 모델 1.7B / 4B | 모델 자체 크기와 능력 | 작은 모델이 가볍지만 태스크 품질이 다름 |
| `num_ctx` | 한 번에 다룰 문맥 창 | 작으면 캐시 부담 감소, 입력/출력 여유 감소 |
| `num_gpu` | GPU에 보낼 레이어 수 요청 | 줄이면 VRAM 감소 가능, CPU 계산 증가 가능 |
| `num_batch` | 입력 처리 배치의 상한 | 작으면 임시 공간 감소 가능, 입력 처리 속도 저하 가능 |
| `num_predict` | 최대 생성 토큰 수 | 총 연산/대기 시간을 제한하지만 가중치를 줄이지 않음 |
| `think` | 추론 토큰 생성 여부 | 쉬운 질문은 빨라질 수 있으나 복잡한 문제 품질 저하 가능 |
| KV cache type | 캐시 저장 정밀도 | 메모리 절약과 수치 정밀도의 절충 |

`num_gpu`는 GPU 개수가 아닙니다. `-1`은 자동, `0`은 CPU, 양수는 레이어 수 요청입니다. 요청값이 실제 배치와 일치하는지는 `ollama ps`, `/api/ps`, 서버 로그로 확인해야 합니다. 설정 지원 여부는 Ollama 버전·백엔드에 영향을 받습니다. [런타임 옵션 소스](https://github.com/ollama/ollama/blob/main/api/types.go)

## 4. 무엇을 측정할까?

### 생성 속도

Ollama의 시간 단위는 나노초입니다.

```python
tokens_per_second = eval_count / (eval_duration / 1_000_000_000)
```

예를 들어 120토큰 생성에 6,000,000,000ns가 걸렸다면 20 tok/s입니다. HTTP 전체 시간에는 모델 로딩, 입력 처리, 통신도 들어가므로 생성 시간과 구분합니다. [Generate API](https://docs.ollama.com/api/generate)

### TTFT와 전체 대기

TTFT(Time To First Token)는 요청부터 첫 토큰이 도착할 때까지입니다. 이 구현은 `response` 또는 `thinking` 필드가 처음 비어 있지 않게 도착한 시점을 기록합니다. Thinking이 켜져 있으면 사용자가 최종 답변을 보기 시작하는 시점보다 빠를 수 있습니다.

`stream=False`로 완성 응답만 받으면 이 시점을 관측하기 어렵습니다. 그래서 NDJSON 스트림을 한 줄씩 읽습니다.

### 메모리와 CPU

요청 전후에 한 번만 보면 중간 사용량 증가를 놓칩니다. 별도 스레드가 CPU·RAM·VRAM을 반복 관측합니다. 그래도 샘플 사이의 순간 피크는 보장할 수 없습니다.

VRAM은 `nvidia-smi`가 보고한 선택 GPU 전체 사용량입니다. RAM은 시스템 전체의 `total - available`이며 프로세스 RSS 합산과 다릅니다. 백그라운드 앱 사용량도 포함됩니다. 실제 Ollama 모델의 VRAM 배치 정보는 `/api/ps`의 `size_vram`을 별도로 보관합니다. [PS API](https://docs.ollama.com/api/ps)

## 5. 공정한 실험 설계

1. 질문, 출력 한도, Thinking, seed와 temperature를 고정합니다. seed가 같아도 하드웨어/구현 차이로 완전한 동일 출력을 보장하지는 않습니다.
2. 각 설정에서 해당 모델만 해제하고 1토큰 워밍업 요청을 보냅니다. 워밍업은 성능 통계에서 제외합니다.
3. 같은 설정을 기본 3회 실행합니다. 속도·대기 시간은 중앙값으로 요약합니다.
4. 메모리는 반복 중 최대값으로 요약합니다. 이것은 실제 최대 메모리의 상한을 보장하지 않습니다.
5. 설정 순서를 고정 seed로 섞어 특정 모델이 항상 마지막에 실행되는 현상을 줄입니다. 열과 전력 상태의 영향이 완전히 사라지는 것은 아닙니다.
6. 실패는 삭제하지 않고 기록합니다. 일부만 성공한 설정은 추천하지 않습니다.
7. GPU 값이 없으면 `null`로 남깁니다. 측정 실패를 0MB로 넣으면 잘못 추천하게 됩니다.

반복 질문의 입력 캐시 재사용은 허용하는 warm benchmark입니다. cold-start 성능이나 캐시 없는 긴 문서 처리와는 다른 실험입니다. 필요한 입력 길이마다 동일한 별도 실험을 만들어야 합니다.

## 6. 최적화 알고리즘은 왜 단순 탐색인가?

첫 버전에서는 Grid Search를 사용합니다.

```text
모델 2개 × 문맥 3개 × GPU 설정 3개 × 배치 1개 = 설정 18개
설정마다 워밍업 1회 + 측정 3회 = 생성 요청 72회
```

후보가 적을 때는 구현이 단순하고 모든 비교를 설명할 수 있습니다. 바로 베이지안 최적화 등을 도입하기 전에 올바른 지표와 재현 가능한 실험을 만드는 것이 우선입니다. UI는 1회 최대 48개 설정으로 제한합니다.

추천은 아래 조건을 모두 통과한 뒤, **각 모델·프로필 안에서** 생성 속도 중앙값이 가장 높은 설정을 고릅니다.

```text
모든 반복 성공
요청한 문맥 >= 필요한 최소 문맥
VRAM과 RAM 관측값 존재
관측 VRAM <= 사용자가 정한 GPU 메모리 한도
관측 RAM <= 사용자가 정한 시스템 RAM 한도
```

문맥과 GPU 레이어는 요청값 기준입니다. 실제 적용 문맥과 배치는 원시 결과로 확인하세요. 자동 품질 검증이 없으므로 이것은 **측정 조건 안에서의 속도 후보 추천**입니다. 실제 작업에서 답변이 충분하고 여유 메모리가 있는지 확인한 뒤 사용합니다.

## 7. GTX 1650 4GB / RAM 16GB에서 진행 순서

1. Qwen3 4B / ctx 2048 / GPU 자동 / batch 128 / Thinking 끄기로 기준 결과를 만듭니다.
2. 같은 조건에서 1.7B를 비교합니다. 속도뿐 아니라 답변을 읽습니다.
3. 4B가 GPU에 일부만 올라가면 ctx 1024, 배치 64, KV q8 실험을 각각 진행합니다.
4. 필요한 문맥이 4096이면 최소 문맥 조건을 4096으로 바꿉니다. ctx 1024 설정이 빨라도 목적에 맞지 않습니다.
5. 메모리 한도는 VRAM 물리 용량 끝까지 잡지 말고 평소 화면·브라우저 사용량 변동을 고려해 여유를 둡니다. 앱의 3700MiB/14000MiB는 출발점이며 PC별로 조절합니다.

RAM이 많다고 VRAM이 같은 속도로 확장되는 것은 아닙니다. CPU에 계산을 맡기는 방식과 매 토큰 데이터를 전송하는 방식 등 구현마다 비용이 달라집니다. 실제 측정으로 판단하세요.

## 8. 다음 단계에서 품질을 넣는 방법

실제 용도의 질문 세트를 만듭니다. 예를 들어 코드 설명 5개, 요약 5개, JSON 추출 5개를 준비하고, 각 질문마다 필수 포함 내용이나 정답 구조를 미리 정의합니다. 그다음 속도뿐 아니라 통과율을 측정합니다.

코드 실행이 필요한 평가는 별도의 격리 환경이 필요합니다. 모델이 생성한 코드를 현재 PC에서 무조건 실행하는 평가기는 만들지 않습니다. 첫 버전은 실제 출력 확인으로 시작합니다.
